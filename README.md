# ПОС — преподавательская оценка студентов

Консольное приложение на Go: студенты, рубрикатор (то есть все критерии),
выставление и исправление оценок, итоги, средний итог группы и экспорт CSV.
Данные хранятся в памяти до выхода, CSV сохраняет только итоги.

## Запуск

```bash
go run . # запуск, демо-версию можно выбрать, выбрав 11
go test -cover ./... # тесты и их покрытие
go vet ./...
```

## Архитектура: Ports and Adapters

- `internal/domain` – ведомость, проверки и расчёт итогов, при этом это не зависит от других слоёв
- `internal/application` – сценарии `Service`, порты `GradebookRepository` и `ResultExporter`, зависит от Domain.
- `internal/adapters` – реализации портов: `MemoryRepository` и `CSVExporter`.
- `internal/console` – меню, ввод и вывод, вызывает сценарии Application.
- `internal/di` – сборка зависимостей через `go.uber.org/dig`, `main.go` запускает консоль через `Invoke`.

Зависимости направлены так: Console → Application → Domain, Adapters → Application / Domain.
Реализации портов выбираются в DI-контейнере и передаются через конструкторы

## DDD

 Единый язык - Студент, критерий, оценка, балл, ведомость и итог одинаково используются в коде и меню 
 Entity – `Student` и `Criterion` различаются по ID, `Evaluation` — по паре ID студента и критерия 
 Value Object – `Score`: собственного ID нет, сравнивается по значению, изменение создаёт новый балл
 Aggregate Root – `Gradebook`: студенты, критерии и оценки одной ведомости, изменения только через её методы
 Repository – Порт `application.GradebookRepository`, реализация `adapters.MemoryRepository`
 Domain Service – `Calculator`: считает итог по оценкам и рубрикатору, итог отдельно не хранится

Одна ведомость объединяет студентов, задания и оценки. В итоге у нас есть группа связанных между собоей объектов, все проверки выполняются через методы ведомости: например перед добавлением оценки проверяется, что нужные студент и задание существуют, а сама оценка допустима.
Студенты различаются по id.
Поля структур закрыты, поэтому менять данные нужно через методы, которые выполняют нужные проверки. Методы, возвращающие списки, отдают только копии, чтобы случайно не поменять список
`MemoryRepository.Get()` возвращает указатель на ведомость, которая хранится в памяти. Изменения сразу сохраняются в памяти

## Правила и расчёт

- Имена непустые, максимум критерия и вес — положительные числа без NaN и бесконечности.
- Балл — от 0 до максимума включительно, без NaN и бесконечности; студент и критерий должны существовать.
- У пары «студент — критерий» одна оценка: повторное выставление исправляет её, ошибка сохраняет старую.
- Студентов и критерии можно добавлять и просматривать; менять и удалять их ТЗ не требует.
  Параметры добавленного критерия неизменны, чтобы максимум не оказался ниже уже выставленного балла.
- Итог: `10 × сумма((балл / максимум) × (вес / сумма всех весов))`.
- Пропущенная оценка даёт 0, её вес учитывается. Веса нормируются; при пустом рубрикаторе расчёт запрещён.
- `Weighted` даёт дробный итог, `RoundedWeighted` округляет до целого, 0.5 вверх. Правило едино для отчёта и CSV.

## Три паттерна

В проекте используются три паттерна:

**Simple Factory** — функция `domain.newEvaluation` проверяет критерий и балл, затем создаёт оценку. Её вызывает метод `Gradebook.SetEvaluation`, который дополнительно проверяет, есть ли студент в ведомости. Для фабрики достаточно одной функции, потому что вид оценки только один.

**Facade** — `application.Service` предоставляет консоли методы для работы с ведомостью. Через него выполняются расчёт и экспорт, поэтому консольному интерфейсу не нужно знать, как они устроены. Перед экспортом сервис пересчитывает итоговые оценки.

**Strategy** — интерфейс `domain.FinalStrategy` позволяет менять способ расчёта итоговой оценки без изменения самой ведомости. В меню можно выбрать одну из двух стратегий. Выбранная стратегия также применяется при экспорте.
